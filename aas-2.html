AAS-2 · Proof of Delivery Standard · draft 0.1

A receipt a stranger can check.

AAS-2 is an open format for proving what an AI service delivered. An agreement defines deterministic checks, the provider signs the output, and the verifier signs a receipt. The receipt commits to every record through a Merkle root, so a buyer can prove one failure without revealing the rest. At L3, three SPL Memo transactions on Solana put the timeline beyond the provider's control.

Three levels of evidence

The same receipt format, with progressively harder-to-fake evidence. A buyer chooses the level the agreement requires.

L1

Verifier signature

The verifier reruns the checks and signs the result. Fast and private, but the timeline rests on one clock.

L2

Both parties sign

Customer and provider sign the agreement. The provider signs the output hashes and timestamp. No chain fees.

L3

Anchored on Solana

Three ordered memos commit to the agreement, output, and receipt. The deadline clock becomes the output anchor block time.

Verify the mainnet proof

Node 18 or later, no install, no wallet. This reads the three mainnet memos, reruns every check, and compares the result with the signed receipt. 

git clone https://github.com/thesithunyein/equxi
cd equxi
node aas2.js verify-receipt \
  --receipt fixtures/aas-2/mainnet/receipt.json \
  --agreement fixtures/aas-2/mainnet/agreement.signed.json \
  --output fixtures/aas-2/output.product-feed.csv \
  --verifier-key .well-known/equxi-verifier.json \
  --provider-key fixtures/aas-2/mainnet/provider.pub.json \
  --report fixtures/aas-2/mainnet/report.json \
  --rpc https://api.mainnet-beta.solana.com

PASS  anchors_on_chain  {"slots":[464339794,464339830,464339908]}
VALID

Twelve checks run. The last three are signature validity, the output anchor clock, and the on-chain memos.

For implementers

The reference verifier is one implementation, not the definition. Anything that produces the same hashes from the same public data conforms.

HTTP

Stateless endpoint

POST https://www.equxi.tech/api/verify takes an agreement and an output, and returns a signed receipt plus a private report.

Identity

Published key

The active receipt key and rotation policy live at /.well-known/equxi-verifier.json. Every receipt carries the key inline.

Ruleset

Five checks

record_count, required_fields, field_types, unique, deadline. Checks are versioned separately from the receipt format.

What a receipt does not prove

Checks are structural. A passing receipt means the delivery matches the agreed format, not that the content is true. A failed check is a verification result, not a legal breach. The verifier is trusted in v0.1; the timeline is only as strong as the level chosen.

AAS-2 is a draft. The version stays 0.x until an implementation written by someone else produces the same hashes, a verifier key rotation has been exercised, and the governance review is done.
